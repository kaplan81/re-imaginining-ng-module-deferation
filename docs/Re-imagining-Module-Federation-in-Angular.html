0 - Angular compilers

This is not a TypeScript decorator

@Component({

  selector: 'cat-bean-grid',

  imports: [CurrencyPipe, DecimalPipe],

  templateUrl: './bean-grid.component.html',

  styleUrl: './bean-grid.component.scss',

})

export class BeanGridComponent { … }

A component decorator. A selector, two pipes it imports, a template file, a stylesheet, and a class underneath.

TypeScript does have decorators. Microsoft added them to the language years ago, and Alex Rickabaugh from the Angular team will tell you they were added largely because Angular needed them. So it would be reasonable to assume this is one of those.

It is not. This is Angular's own decorator, and it behaves nothing like TypeScript's.

A TypeScript decorator is a function. It runs. At runtime, when the class is defined, the function is called and it can do something to the class.

This one never runs. In the build that reaches your users it is not there at all — open the bundle and search for the word Component and you will not find it. It was read at compile time, by a compiler, and then deleted.

Everything inside those braces is metadata. A description. The selector is a description of how to find this component in HTML. The imports are a description of what the template is allowed to use. The HTML is metadata. The SCSS is metadata. None of it is code that runs.

So if it is a description rather than instructions, something has to read it and turn it into something that does run.

That something is what the next few minutes are about.

It is an Angular definition

class BeanGridComponent {

  items = input.required(); // your code, unchanged

  stockState(bean) { return bean.stockKg < 60 ? "low" : … } // unchanged

 

  static ɵfac = (t) => new (t || BeanGridComponent)(); // added

  static ɵcmp = ɵɵdefineComponent({ // added

    type: BeanGridComponent,

    selectors: [["cat-bean-grid"]], inputs: { items: [1, "items"] },

    template: function (rf, ctx) {

      rf & 1 && ( ɵɵdomElementStart(0, "ul", 0), ɵɵrepeaterCreate(1, …), ɵɵdomElementEnd() );

      rf & 2 && ( ɵɵadvance(), ɵɵrepeater(ctx.items()) );

    }

  });

}

rf & 1 — create. Runs once. Builds the DOM.

rf & 2 — update. Runs on every change detection.

Here is the same component after compilation. Nothing is simplified except the parts replaced with an ellipsis.

Start at the top, because the top is the surprising part. Your class is still your class. The field is still a field. stockState is still an ordinary method, with the same ternary you wrote. If you pasted that class into the TypeScript playground with the decorator removed, you would get almost exactly these lines. The compiler did not touch your code.

What it did was add two static properties, and delete the decorator.

The first one, ɵfac, is the factory — how to construct this class, and what to inject when you do.

The second is ɵcmp, and this is where everything from the decorator went. The first property in it is type, and it points straight back at the class above it — this definition belongs to that class, and the runtime follows that reference in both directions. Then the selector is here. The inputs are here. And the template — the HTML file, the one sitting next to the component — has become a function.

Two arguments. rf and ctx. rf is a bitmask, and the function has two halves. One runs when the view is created and builds the DOM. The other runs on every change detection pass and updates it. The whole of Angular's rendering model is in those two lines: build once, update many times.

You do not need to read the instructions. What matters is the shape of what you are looking at — because this is plain JavaScript. Function calls and object literals. No decorator, no HTML, no SCSS, no Angular syntax of any kind. Every bundler on earth can read this.

The template syntax, the decorator, the separate files — all of that is for us. By the time it ships, it is a function.

The Angular compiler wraps the TypeScript compiler — so everything Angular does to your code has to fit through TypeScript’s own compiler API.

So what is the thing that deleted your decorator? It is called ngc — the Angular Compiler — and it ships as a real command in at-angular-slash-compiler-cli. Alex Rickabaugh describes it as an extended TypeScript compiler which also knows how to execute Angular decorators, applying their effects at build time instead of run time.

You will see a second name on this slide, and it is worth one sentence so it does not distract you. Ngtsc is what the implementation is called inside Angular's source — ng, plus tsc — which is why these three classes are named the way they are. Same compiler. Ngc is what it is called from outside.

The architectural fact underneath that is this: it does not replace the TypeScript compiler, and it is not a fork of it. It wraps it. NgtscProgram wraps TypeScript's Program. NgCompilerHost wraps TypeScript's CompilerHost — that is how it sneaks in extra files, like the template type-checking shims. And NgCompiler sits on top and drives all the Angular-specific work.

Angular's own documentation puts it bluntly: the decorator is the compiler. @Component is not configuration that gets read at runtime. It is an instruction to a compiler, and the compiler's entire job is to turn it into something else.

Because it wraps TypeScript rather than replacing it, everything Angular does to your code has to fit through TypeScript's own compiler API. Angular does not get to invent its own way in. It uses the doors TypeScript leaves open.

That constraint is what gave Angular ten years of unusually good tooling — one compiler pass, one type system, Angular semantics and TypeScript semantics checked together.

All six run for every decorated class — component, directive, pipe, service.

The backend produces two outputs from the same analysis: the type-check blocks, and the code that replaces the decorator.

Frontend — understands decorators and how they are interconnected. Global and slow.

Backend — transforms file by file. Local and fast.

Six phases, and every decorated class goes through all six.

Every phase here exists to compile the decorator. That is the entire job. Your class body, your methods, your types — none of that enters this pipeline. It goes through TypeScript exactly as it always would.

And it is every decorator, not only components. A pipe goes through these six. A service goes through these six. Only the template work is component-only.

Detect finds the decorated classes. Analyze reads what is inside each decorator.

Resolve is the one that needs the rest of your program. A template says cat-bean-grid, or uses the currency pipe, and the compiler has to find the class behind that name. The answer is not in the file. It is spread across your imports and your NgModules, so this phase cannot finish until it has seen everything.

Those first three are the whole of the frontend. Nothing has been written anywhere yet — it is all metadata, held in memory.

Everything after them is the backend, and the backend's job is to generate code. It does that twice, from the same analysis, and the two outputs do not depend on each other.

The first is the one nobody guesses. TypeScript cannot read Angular templates. So Angular rewrites each template as TypeScript — a Type Check Block — lets TypeScript's own checker find the errors, maps them back onto your HTML, and drops the blocks. They never reach disk and they never ship. That is where the error comes from when you misspell a property inside double curly braces.

The second output is the code that actually runs. Two phases build it, and they look like one. The difference is small but it is worth having.

Compile builds the definition. For a component, defineComponent gets built, ready to be assigned to ɵcmp. But at the end of compile nothing has been written anywhere. It is an object in memory, in Angular's own format. Your class has not changed yet and your decorator is still on it.

Emit is where it lands. Angular translates that object into TypeScript's own form, puts it on the class as a static property, deletes the decorator, and prints the file.

So compile makes the content. Emit makes the file.

And emit is the only one of the six that writes back into TypeScript. It runs as a TypeScript custom transformer — ts.Transformer. The first five read from TypeScript's compiler; this is the one that hands it something. Angular gives TypeScript a function, and TypeScript calls it during its own emit.

One detail that surprises people: what gets printed is not always JavaScript. This repository sets isolatedModules, which tells Angular to apply only its own transformation and leave the rest of the TypeScript alone. So what the bundler receives here is TypeScript, and esbuild or Rspack does the rest.

Now the two halves. The frontend understands the decorator: global, and slow, because it cannot finish until it has seen everything. The backend writes code — both kinds of it: file by file, and fast. Only one of those halves has been rewritten so far.

0 - Angular compilers

The APIs Angular needs are gone

“The Angular compiler implements its own code transformations via the ts.Transformer API which is not available cross-language.”

Angular blog · An update on Angular’s TypeScript 7-powered Compiler · September 2026

1

TypeScript 7’s compiler is a program written in Go. Stable since July 2026.

2

ts.Transformer is only possible while both sides are JavaScript.

3

Go and JavaScript cannot share objects. So those APIs cannot be made public again

And then this happened.

TypeScript 7 shipped in July. Same language, same type system, but the compiler itself has been rewritten in Go, and it is roughly ten times faster.

Here is the Angular team's own sentence about what that costs them. The Angular compiler implements its own code transformations via the ts dot Transformer API, which is not available cross-language.

Three steps to see why, and they are worth taking slowly.

One. The new TypeScript compiler is a Go program. Not JavaScript that got faster — a different language, compiled to a binary.

Two. ts.Transformer is not a file format and it is not a protocol. It is TypeScript calling a JavaScript function that Angular supplies, handing it a live object — the syntax tree — letting Angular rearrange that object in place, and then carrying on with the result. Both sides are JavaScript. Both sides are in the same process. They are pointing at the same objects in the same memory.

Three. Go and JavaScript cannot do that. You can send data between them — text, JSON, bytes down a pipe. What you cannot do is hand a Go program a JavaScript function and have it call you back with a live tree.

So this is not an API that got harder to use, or changed shape, or needs a wrapper written for it. A set of APIs that used to be public simply cannot be public any more, because there is no way to express them across two languages. Angular will use TypeScript 7's interop for type-checking and diagnostics, where sending data is enough. For compilation and transformation, sending data is not enough.

Which means the capabilities TypeScript used to provide, Angular now has to provide itself.

Two things changed. One is interesting. The other is the one that matters.

The interesting one is the frontend. The orange half — the global, slow half — has been rewritten in Rust, on oxc — the same toolchain underneath Vite. It is multithreaded, which is why it will be fast. The blue half did not move: the backend is still TypeScript, still the same template compiler Angular has always had. What changed in it is only the last step. The old backend handed its result to TypeScript, through ts.Transformer, which is why it had to run inside TypeScript. The one that matters is in the shape of the picture, not in either box.

Look at the top row. The compiler is inside the bundler. That was not a design choice anybody made for fun — it was forced. Angular's output never existed anywhere you could pick it up. It was a syntax tree, inside a running TypeScript process, for a few milliseconds. The only way to receive it was to be in that process, as a plugin. So the bundler had to host Angular's compiler inside itself.

Which is why every bundler that builds Angular needs an adapter written specially for it. Somebody has to write the plugin that drives the compiler and hands the results around. That is what @nx/angular-rspack is. That is what the Analog plugin is for Vite. Somebody maintains each one.

Now look at the bottom row. The compiler runs first, on its own, and leaves two files behind — one per job. The ng dot ts file is your code with the decorator already replaced; that is what the bundler takes. The ngtypecheck file is the templates rewritten as TypeScript; that is what tsc takes, to give you template errors. Same two jobs as before, but now each one ends in a file instead of inside somebody's process. And that is not a plan — it is already there. There is a command in the branch today: you point ngp at a tsconfig, give it an output directory, and it writes you a folder of TypeScript. No bundler involved, nothing hosting anything. Ordinary TypeScript, with the decorator already replaced by the definition.

The bundler is no longer hosting anything. It is just reading TypeScript — which every bundler on earth already does. esbuild reads it. Rspack reads it. Vite reads it. Something you write this afternoon reads it.

The adapter has nothing left to adapt.

1 - Modules

Let us start from the beginning

import { Component } from '@angular/core'

That quoted string is a specifier. It names a module — in practice, a file — but says nothing about where that file is.

Something has to turn it into a file a browser can fetch.

So: who turns that string into a file?

Here is a line that has to appear in every component file ever written, because the decorator has to come from somewhere. Import Component, from at-angular-slash-core.

Look at the part in quotes. That string has a name — it is called a specifier — and the thing worth noticing is what it is not.

It is not a path. It is not a file name. It is not a URL. There is no folder called at-angular-slash-core sitting on a disk somewhere, and there is certainly no file by that name on a web server.

It is a name. Somebody, at some point, has to look that name up and decide which actual file it means.

A browser cannot do that on its own. Hand a browser that string inside an import and it will refuse it — failed to resolve module specifier — because as far as the web platform is concerned, that is not an address at all.

So something has to resolve it. What that something is, and when it runs, is not the same in every Angular application.

The four types of specifier

TypeExample
Relative URL path./util.js
Absolute URL path/lib/util.js
Full URLhttps://cdn.example/x.js

The first three tell a browser where the module’s file is. A bare specifier does not.

There are four types, and the difference between them is the whole of this section.

A relative URL path. Dot-slash util-dot-js. Relative to the file doing the importing.

An absolute URL path. Slash-lib-slash-util-dot-js. From the root of the site.

A full URL. A complete address, pointing at any server you like.

And a bare specifier. At-angular-slash-core — the one from the slide before.

The first three are locations. A browser can take any of them and go and fetch the file, with no help from anybody. The third one could be pasted into an address bar.

The fourth is not a location. There is no server anywhere with a folder called lodash. It is a name, and names have to be looked up by somebody.

And this is the type that matters here, because it is the only one a browser cannot resolve by itself. At-angular-slash-core. Rxjs. Names, with no location attached.

Which is why handing a browser a bare specifier gets it refused — failed to resolve module specifier. Not because the file is missing. Because nothing ever told it where to look.

Static imports and dynamic imports

Static

import { Component } from '@angular/core';

Only at the top of a file.

This is what tree-shaking is built on.

Dynamic

const routes = await import('./catalog.routes');

Anywhere code can go. Returns a promise.
Resolved when the line runs.

A static specifier is known before the program starts. A dynamic one does not have to be.

A specifier does not only turn up in one place.

On the left is the one everybody knows. A static import, at the top of the file. The specifier is written there as a literal string, and it cannot be anything else. You cannot build it, you cannot pass a variable, you cannot read it from a configuration file.

That restriction sounds like a limitation. It is actually what makes the whole build pipeline possible. Because every static specifier is a literal, a tool can read your entire program without running a single line of it, follow every import, and know the complete list of files in advance. That is what lets a bundler build a graph. It is also what lets it shake the tree, because it can see what is never reached.

On the right is the other one. A dynamic import. It is not a statement, it is an expression — it goes anywhere a function call can go, and it hands back a promise.

And its specifier is not required to be a literal. It can be a variable. It can be assembled from a string. It can be a value that did not exist anywhere when the application was compiled.

So the difference that matters is this one. A static specifier is known before the program starts. A dynamic specifier does not have to be — it can be decided while the application is already running.

All of this has a name. It is called module resolution, and it is one job: take a specifier, and work out which file it means.

What is worth knowing is that the job can happen at three completely different moments, and that the choice between them changes a great deal about how an application is built and shipped.

The bundler can do it, before anything ships at all.

The browser's own loader can do it, by itself, as the page loads.

Or a loader you shipped with the application can do it, while that application is already running.

Three moments. One at a time.

Three moments, one at a time. This is the first, and it is the one almost everybody is already using without thinking about it.

At build time, the bundler does the resolving. It reads a specifier, goes looking on the file system, finds the package inside node_modules, and writes the answer into the output.

Here is what that looks like. On the top line, what was written in the source: at-angular-slash-core. On the bottom, the file that came out of the build. The bundler has taken the package, bundled it into a chunk, given it a name of its own and a content hash so it can be cached forever.

And notice what is no longer there. The name is gone. Nothing in that output needs looking up any more, because the lookup already happened — on a machine, months or minutes ago, with a disk full of packages on it.

Which is the thing to hold on to, and the reason the other two moments exist at all. The bundler could do this because node_modules was sitting right there. A browser has no node_modules. <script type="importmap">

  "@angular/core": "/assets/core-DG2k.js",

No library. This is the browser’s own loader — and the map has to be in the page before the first import runs.

A web standard, available in every major browser since 2023.

Second moment. This one is a browser feature, and a surprising number of people have never seen it.

It is a script tag, with a type of importmap, and inside it a piece of JSON. The JSON says: when any module asks for at-angular-slash-core, fetch this file instead. When anything asks for rxjs, fetch that one.

That is the whole mechanism. There is no library here. Nothing was installed. This is the browser's own module loader doing the lookup, using a table it was handed.

Two things are worth knowing about it.

The first is timing, and it is strict. The map has to be in the document before the first module import runs. Not shortly after. Before. Which is why applications that rely on it split their startup into two files — one tiny script that installs the map, and then a second one that actually starts the application.

The second is that it is not new and it is not experimental. Import maps are a web standard and they have worked in every major browser since 2023. No polyfill, no bundler plugin, no runtime.

So here a bare specifier does reach the browser, and the browser can resolve it — because somebody handed it the answers in advance.

That URL did not exist when the application was built. It was fetched, or computed, while the app was already running.

Only possible with a dynamic import — a static one needs a literal.

Third moment, and this is the one that behaves differently from the other two.

Here the resolving is done by code. Not by a bundler on somebody's machine, not by the browser's loader — by JavaScript that was shipped as part of the application and is running right now.

Two lines. The first asks something for an address. That something could be anything: a registry object, a fetch to a JSON file on a server, a lookup in a table that was downloaded a second ago. The second line takes whatever came back and imports it.

And the important word in that is whatever. The address on the second line did not exist when this application was compiled. Nobody wrote it down. It was not in any configuration file that went through the build. It arrived while the application was running, and the application acted on it.

That is a genuinely different capability from the other two moments, and it is the reason this one needs a dynamic import. A static import needs a literal string, decided before anything runs. This cannot be a literal, because the value is not known yet.

So: three moments. The bundler, before anything ships. The browser's loader, before the application starts. And code, while it is already running.

Three answers to the same question. Which one an application picks turns out to decide a great deal about how it is built, how it is deployed, and what can change without rebuilding it.

2 - Module Federation

Modules can be federated

Code splitting

Chunks from your own build.
Fetched when they are needed.

Federation

Chunks from a different build,
on a different server.

Code splitting: one build. Federation: several builds, interconnected.

Each federated module has its own build, its own deployment, its own URL.

The one that loads is the host. The one being loaded is the remote.

We have spent a while on modules, so let us put federation where it belongs. It is something that can happen to a module, and the closest thing to it is something everybody here already does.

Code splitting. A dynamic import, a chunk that is not downloaded until somebody opens that route. Nothing about that is exotic any more.

Federation is the same shape, with one thing changed. The chunk comes from a different build. A different compile, on a different schedule, deployed to a different server — and your bundler never saw it.

So it is not bundled against not bundled. Both of these are bundles. Both arrive on demand. The only difference is which build produced the thing you are fetching, and that single difference is what forces the resolution into the third moment. Your build could not have resolved an address that did not exist yet.

Worth comparing to how this is normally done, because the contrast is sharp. Today, if one team has a component another team wants, it goes to a registry: publish the package, the other team installs it, rebuilds their entire application, and deploys. Three steps and two builds, for a change of text.

Federated, the first team deploys. That is the whole procedure. The second application points at a URL and picks up whatever is there the next time somebody loads the page.

Three consequences, and they are the whole of what this buys.

Independence. A federated module has its own build, its own deployment, its own URL.

The dependency can point both ways. This is not a parent and a child. Two applications can each load from the other, and in real systems they often do.

And the vocabulary, which everything after this uses. In any one exchange, the side doing the loading is the host. The side being loaded is the remote. Roles in a transaction, not ranks — which is why both ways round is possible at all.

So that third moment — resolving a name while the application is already running — has a name of its own once somebody wraps a protocol around it. It is called Module Federation.

And the first thing to say is the thing most people have backwards. It is not a library. It is a mental model: a few roles, and a contract between them. Implementations exist, several of them, and they are quite different pieces of software — but what they implement is this picture.

Three applications. Look at them before anything else and notice that they are the same kind of thing. Not a framework and its plugins. Not a parent and its children. Three identical boxes.

Only the labels differ. One is playing host — and an application in that role is usually called the shell. The other two are playing remote.

What a remote offers, it offers by name. One of these exposes its routes, the other exposes widgets, and that is all either of them offers. Everything else inside stays private; the host has no way to reach it.

One thing only the host has, on the left. A manifest: a short file that says which remotes exist and where to find each one. In the application we will run later it is a few lines of JSON — a name, and the URL of that remote's entry. The remotes do not have one, and do not need one. They are not looking for anybody.

Now the part worth pausing on. Every one of the three publishes a remoteEntry. Not just the remotes. The host does too, and in the application we will look at later the shell's remoteEntry lists no exposes at all — an empty array — while still carrying the full shared table.

Which tells you that host and remote are not opposites, and not ranks. They are roles. The same application can be a remote to the thing above it and a host to something it loads itself, at the same time.

And look at the arrows, because they run both ways on purpose. A remote is not only a thing that gets consumed. It can consume back — load something the host exposes, or something a sibling exposes. The relationship is allowed to be circular, and in real systems it often is. Nothing in the model says this has to be a tree.

And because each one is served from its own URL, you can simply open a remote in a browser and use it on its own. It is a complete application. It does not need the shell to exist.

Which is also what makes the addresses changeable. None of this was decided at build time, so a remote can move tomorrow, or a new one can appear, and nothing has to be rebuilt for that to work.

Then the band along the bottom: shared. Without it, three applications each bring their own Angular, and the browser runs three copies of the framework with three injector trees. Shared is the agreement that stops that — and it is more than a list of names. Each entry carries the version range it needs, the version it was built against, and whether it must be a singleton. At load time those get negotiated, and one copy wins.

That model has been implemented twice, and these two are what the rest of the talk compares.

The first keeps the name. Module Federation, the packages under at-module-federation, the one that started in webpack and now runs on Rspack and on Vite as well. The second is Native Federation, from the Angular Architects team — the same model rebuilt on web standards instead of on a bundler's internals.

Three rows, and the first one causes the other two.

Who resolves. Both of them have a loader — the difference is whose. Module Federation ships one with your application, and it reads from a structure it keeps in memory called the share scope. Native Federation uses the loader the browser already has, and that one reads from an import map.

The paths. Module Federation never writes them down anywhere, so the code is asked again every single time something is needed. Native Federation negotiates everything at boot, writes the result into the import map, publishes it, and from then on the browser handles every lookup.

And the last row is where it bites. Module Federation can be told to override a remote it has already registered — registerRemotes, with force. Be precise about what that does, because the name invites the wrong picture: it does not edit a path. It finds the registration by name, tears the old one out, and pushes an entirely new one in its place. The library warns you while it does it — the remote is already registered, and overriding it may cause unexpected errors.

Native Federation cannot do that, and the reason is not that somebody forgot to write the function. It is the web platform itself. Add a second import map to a page that already has one and the browser accepts it quite happily — new names work. But give it a name the first map already defined, and the new value is silently ignored. No error, no warning. The first mapping wins, for the lifetime of that page.

So once the map is published, those paths are final. Not by choice.

The simplest way to hold all of it: one of them writes the answer on a note and pins it to the door, and from then on everyone reads the note. The other keeps a librarian, and you ask her every time.

A build tool has defaults. For example Rsbuild compiles .ts with no configuration whereas Rspack needs a rule pointing at a loader.

Last section, and it is about the thing that actually assembles your application.

It starts with a distinction that gets skipped almost everywhere, including in the earlier version of this talk. And there is a one-sentence version of it worth borrowing: build tools have defaults, and bundlers do not.

Start at the top, and the important word is contains. A build tool holds a bundler inside it, and then a great deal more around it.

Take Rsbuild, since it is on the table. Rspack is in there, doing the bundling. But so is a dev server, so is the thing that compiles your TypeScript, so is the stylesheet pipeline, so is the handling of images and fonts. You install one package and all of it arrives together.

So a build tool is mostly not bundling. It is everything around the bundling — which is why one command gives you a working application instead of a configuration file. Vite is a build tool. Rsbuild is a build tool.

Underneath it, a bundler has a much narrower job. It takes your module graph — every file and every import — and splits it into chunk files. Deciding how many there are and which modules go in each one is the whole of code splitting. That is what a bundler does, and it will not guess at anything you have not told it.

The line underneath is the clearest example of the difference, and the two names in it sit on the same row of the table. Rsbuild and Rspack come from the same team, and Rsbuild is built on Rspack. Hand Rsbuild a TypeScript file and it compiles it — nothing to configure, it already knows. Hand the same file to Rspack and nothing happens, because Rspack has no opinion about what a dot-ts file is. You write a rule that says: for files matching this pattern, use this loader.

Same compiler underneath, in both cases. One of them decided for you. That is the whole distinction.

Which is also why the name people say out loud is almost always the one on the left of this table. You say you are using Vite. The thing doing the bundling is Rolldown. You say ng build. The thing doing the bundling is esbuild. Most people have never needed to know the second column exists.

And the two layers move independently. Vite used to bundle with Rollup, and used esbuild for part of its work. As of Vite eight, esbuild is not a dependency at all any more and Rolldown is underneath. The build tool kept its name. The bundler changed.

So when the next slide says three pipelines, it means three combinations of these two layers — and that is before federation enters the picture at all.

The top row is the one everybody has. A file called angular dot json, the command ng build, the plugin at-angular-slash-build, and esbuild underneath. Most people have never needed to know the last two are there.

Rspack dot config dot ts and rspack build, which loads a plugin from Nx and lands on Rspack. Vite dot config dot ts and vite build, which loads the plugin from the Analog project and lands on Rolldown.

One word of precision on that last one. Vite is not a bundler — it is a build tool. The bundler underneath it is Rolldown, which is why the column says Rolldown and not Vite.

So how do these plugins actually work? All three do the same job through three different plugin APIs. Each registers with its bundler and says: before you read a TypeScript file, hand it to me first. The plugin runs the Angular compiler on it and gives back the result. esbuild calls that hook onLoad. Vite calls it transform. Rspack does it through a plugin of its own. The compiler is the same every time. The hook is not — which is exactly why there has to be one of these per bundler, and why somebody has to maintain each one.

Now the last column, and it is the thing that is easiest to get wrong. It was got wrong in the earlier version of this talk.

There are two choices on this table, and they are independent. The bundler is one. The federation library is the other. Six combinations are possible and three of them are in this repository. Module Federation on esbuild is not here. Native Federation on Rspack is not here. Nothing stops either from existing — they simply are not built.

So keep the two apart for the rest of this section. If something is true of build two, it might be a fact about Rspack. Or it might be a fact about Module Federation. Those are different claims, and from one build you often cannot tell them apart.

3 - Bundlers

Vite pipeline

Why it is probably not an option

There is no federation reason to use Vite, unless you are very interested in its ecosystem.

Chunk URL rewriting is not possible.

Unused shared modules are not automatically pruned.

There is no real advantage over the Angular CLI capabilities.

So: the two custom pipelines, one at a time, each against the thing you already have. The weaker case first.

The first line is the honest headline. There is no federation reason to reach for Vite. What you would gain on the federation side does not come from Vite, it comes from Module Federation — and it is the same whichever bundler you run it on. What Vite does give you is its own ecosystem: Vitest for testing, Storybook for components in isolation, Astro if you are putting Angular into a documentation site. If you want that, want it for itself.

Chunk URL rewriting is not possible, and the reason is Rolldown. It writes real import statements into the output with the paths inside them. The address of a chunk is in the statement, so there is no variable anywhere to reassign while the application is running.

Shared modules are not pruned for you, and this one costs real bytes on the day. The federation plugin emits a chunk for every package you declare as shared, not for every one you actually use. Declare all your dependencies and the Angular compiler — six hundred kilobytes of it — ships into every application, for nothing. The Angular CLI prunes that automatically. Here you keep the list by hand.

And the last line is the summary of the other three. Against the capabilities the CLI already gives you, there is nothing here you are gaining.

3 - Bundlers

Rspack pipeline

Why it could be an option

Runtime plugins for extending federation behaviour.

Hooks around the federation lifecycle.

Chunk URL rewriting is possible, unlike in Native Federation.

The loader itself, remoteEntry.js, is replaceable.

Seamless integration with Zephyr Cloud.

Now the other one, and here there is a case.

Runtime plugins, and hooks around the federation lifecycle. The federation runtime exposes a registration API for both, so you can extend what happens when a remote is resolved, loaded or shared. There is nothing equivalent on the other side.

Chunk URL rewriting. Rspack works out every chunk address from a variable it keeps in the runtime it ships with your application, so those addresses can be moved while the application is live. Native Federation never writes them anywhere you can reach.

The loader is replaceable. A remote entry here is executable JavaScript rather than a manifest of data, which means it can be swapped, wrapped or generated. A JSON file cannot.

And Zephyr Cloud builds on exactly those last two. Deploy a remote, every host picks it up, with version history and rollback, and nobody rebuilds anything.

One caution to keep in your pocket. Seven of this bundler's defaults turned out to be silently fatal once federation was in play, and three of them broke only the dev server while the production build stayed green. That is not on the slide, but it is the thing you will meet in week one.

3 - Bundlers

What ngp changes about all of this

It compiles one file at a time, so a bundler plugin can compile only the files a page actually reaches. That is lazy compilation, and it takes over part of what Module Federation is for.

It can do separate builds, like Module Federation does — but not separate deployments, because the minimal deployable unit is the app.

Today

Every bundler that is not esbuild needs an adapter to host the Angular compiler. The adapter (or plugin) sets the ceiling.

With ngp

The compiler leaves a file. The bundler reads TypeScript. There is nothing left to adapt.

It makes Angular more pluggable.

So that is the whole argument, and there are two halves to it.

The first half is lazy compilation. ngp can be asked for one file, and both halves of the compiler move together — the analysis and the code generation, for that one file, in one call. The old compiler could not do the analysis half without building a program over everything, so a per-file unit did not exist to ask for. Now it does, and a bundler plugin can ask for a file only when something actually wants it. One exception: packages do not go through this. Node modules are handled once, up front, by Angular's linker. Your own code is the lazy half.

So why does a team split an Angular application into separately built pieces? Ask them and you hear about autonomy. Ask what actually drove the decision and it is more ordinary. The build got slow. Somebody waits minutes to see a change in a corner of the application they are not even touching. That is a build-time problem solved with a runtime architecture — a very large bill for a fast feedback loop.

Hence that second line. Separate builds is the thing you no longer need federation for. One codebase, one build, and the compiler still only looks at what the page needs. This is not hot module replacement, in case anybody hears it that way — that swaps a piece of an application already built. This is about never building those pieces at all.

Somebody will push back on the sharing, so have the answer ready. Federation really does guarantee one copy of Angular. But inside a single build you get that for nothing, and more firmly: the bundler resolves the specifier to one module, and every importer gets that instance. Sharing is a fix for a problem separate builds create. Five builds means five copies. One build never had five.

Separate deployments is what no compiler reaches. One build is one deploy. No shipping your piece on Tuesday while another team ships theirs on Thursday, no two Angular versions side by side. All of that follows from separate deployments, and separate deployments is federation's alone.

Notice the floor, though. The smallest thing you can deploy separately is a whole application. The widget microfrontends in this repository look like components and are not — each is a full project, with an entry point, a bootstrap, three tsconfigs, its own design tokens and a dev server port. To ship one component you build an application around it. Which is the real difference in grain: federation separates at the application, lazy compilation separates at the file. So lazy compilation does not replace Module Federation. It replaces the reason most teams reached for it.

The second half is the two lines underneath, and it is why this talk exists now rather than a year ago. Every bundler that is not the one Angular ships with needs an adapter whose only job is to host the Angular compiler, because until now Angular's output never existed anywhere you could pick it up. One adapter per bundler, each maintained by somebody, each one a ceiling — and you find out which ones are still maintained on the day you try to upgrade. When the compiler leaves a file behind, the bundler is not hosting anything. It is reading TypeScript, which all of them already do. The adapter has nothing left to adapt.

None of that is shipped. It is a prototype in a branch, and the caution in its README is their own word. But it has been merged, it is worked on every day, and the direction is not ambiguous.

So if you take one thing: the bundler under your Angular application is a decision, it already was, and the thing that made it expensive is being removed. That is what the last line means. Angular becomes pluggable.

Everything here — five applications, three pipelines, fifteen dev servers, the measurements and how they were taken — is in that repository. Clone it, and disagree.
