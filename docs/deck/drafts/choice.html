Compilation stops living inside the bundler

Today

ngtsc runs inside the bundler

As that bundler’s own plugin. No intermediate compiled JavaScript ever exists.

So every other bundler needs a bespoke Angular adapter.

Where it is heading

ngp emits a file, before it

Angular’s words: that output “can be fed to TypeScript or directly to a bundler.”

A bundler handed plain TypeScript needs no adapter.

So your bundler stops being a constraint and starts being a choice.

Here is why I dragged you through a compiler slide. Today, Angular compilation does not happen before your bundler runs. It happens inside it. ngtsc is installed as that bundler’s own plugin — an esbuild plugin for the CLI, a loader for Rspack, a plugin for Vite. There is no folder of compiled JavaScript sitting between the two. That is why you cannot just point any bundler at an Angular project. It means every bundler that is not the one the CLI ships needs somebody to write and maintain an Angular adapter for it. Hold on to that word, adapter. It comes back later, and it turns out to be the most expensive word in this talk. Now look at the right-hand column. ngp does not install itself into your bundler. It emits a file. And the Angular team’s own wording is the part worth quoting — that output can be fed to TypeScript, or directly to a bundler like esbuild. A bundler that is handed plain TypeScript does not need to know what a component is. It does not need an adapter at all. I want to be careful here, because this has not shipped. It is pre-MVP, the experimental release is aimed at the end of this year, and the CLI integration is still a prototype. So I am not telling you the adapter problem is solved. I am telling you which direction Angular is walking, and that the commits are landing daily. And if that is the direction, then the question this talk is about becomes a real one rather than a theoretical one: if your bundler is a choice, what does each choice actually cost you?
