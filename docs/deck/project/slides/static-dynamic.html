Static imports and dynamic imports

Static

import { Component } from '@angular/core';

Only at the top of a file.
The specifier must be a literal string, so the whole graph is known before anything runs.
This is what tree-shaking is built on.

Dynamic

const routes = await import('./catalog.routes');

Anywhere code can go. Returns a promise.
Resolved when the line runs.
The specifier can be a variable.

A static specifier is known before the program starts. A dynamic one does not have to be.

A specifier does not only turn up in one place. On the left is the one everybody knows. A static import, at the top of the file. The specifier is written there as a literal string, and it cannot be anything else. You cannot build it, you cannot pass a variable, you cannot read it from a configuration file. That restriction sounds like a limitation. It is actually what makes the whole build pipeline possible. Because every static specifier is a literal, a tool can read your entire program without running a single line of it, follow every import, and know the complete list of files in advance. That is what lets a bundler build a graph. It is also what lets it shake the tree, because it can see what is never reached. On the right is the other one. A dynamic import. It is not a statement, it is an expression — it goes anywhere a function call can go, and it hands back a promise. And its specifier is not required to be a literal. It can be a variable. It can be assembled from a string. It can be a value that did not exist anywhere when the application was compiled. So the difference that matters is this one. A static specifier is known before the program starts. A dynamic specifier does not have to be — it can be decided while the application is already running. [Two columns.
