1 - Modules

Runtime — code you shipped resolves it

const url = registry.lookup('catalog');

const mod = await import(url);

That URL did not exist when the application was built. It was fetched, or computed, while the app was already running.

Only possible with a dynamic import — a static one needs a literal.

Third moment, and this is the one that behaves differently from the other two. Here the resolving is done by code. Not by a bundler on somebody's machine, not by the browser's loader — by JavaScript that was shipped as part of the application and is running right now. Two lines. The first asks something for an address. That something could be anything: a registry object, a fetch to a JSON file on a server, a lookup in a table that was downloaded a second ago. The second line takes whatever came back and imports it. And the important word in that is whatever. The address on the second line did not exist when this application was compiled. Nobody wrote it down. It was not in any configuration file that went through the build. It arrived while the application was running, and the application acted on it. That is a genuinely different capability from the other two moments, and it is the reason this one needs a dynamic import. A static import needs a literal string, decided before anything runs. This cannot be a literal, because the value is not known yet. So: three moments. The bundler, before anything ships. The browser's loader, before the application starts. And code, while it is already running. Three answers to the same question. Which one an application picks turns out to decide a great deal about how it is built, how it is deployed, and what can change without rebuilding it. [Two lines of code. The weight is on "did not exist when the application was built".]
