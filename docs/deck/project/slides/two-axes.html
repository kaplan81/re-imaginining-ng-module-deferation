A custom pipeline is a config file and a plugin. Same five applications, same feature code, three times.

Last section, and it is the one the whole talk has been walking towards. Everything so far has been one application at a time. Now the same product, built three different ways, running side by side. Five applications — a shell, two page remotes, two widget microfrontends. The feature code is byte-identical across all three builds; only the pipeline changes. Read the table left to right, because that is the order the decision happens in. You pick a pipeline. The pipeline loads an Angular plugin. The plugin determines which bundler ends up doing the bundling. The top row is the one everybody has. A file called angular dot json, the command ng build, the plugin at-angular-slash-build, and esbuild underneath. Most people have never needed to know the last two are there. The other two are custom pipelines, and that phrase is doing real work. There is no angular dot json involved and the ng command never runs. Rspack dot config dot ts and rspack build, which loads a plugin from Nx and lands on Rspack. Vite dot config dot ts and vite build, which loads the plugin from the Analog project and lands on Rolldown. One word of precision on that last one. Vite is not a bundler — it is a build tool. The bundler underneath it is Rolldown, which is why the column says Rolldown and not Vite. So how do these plugins actually work? All three do the same job through three different plugin APIs. Each registers with its bundler and says: before you read a TypeScript file, hand it to me first. The plugin runs the Angular compiler on it and gives back the result. esbuild calls that hook onLoad. Vite calls it transform. Rspack does it through a plugin of its own. The compiler is the same every time. The hook is not — which is exactly why there has to be one of these per bundler, and why somebody has to maintain each one. Now the last column, and it is the thing that is easiest to get wrong. It was got wrong in the earlier version of this talk. There are two choices on this table, and they are independent. The bundler is one. The federation library is the other. Six combinations are possible and three of them are in this repository. Module Federation on esbuild is not here. Native Federation on Rspack is not here. Nothing stops either from existing — they simply are not built. So keep the two apart for the rest of this section. If something is true of build two, it might be a fact about Rspack. Or it might be a fact about Module Federation. Those are different claims, and from one build you often cannot tell them apart. [Walk the table left to right, then stop on the last column. Two choices, not one.]
