## 2 · `decorator` — This is not a TypeScript decorator

*Transition: fade*

**On screen**

- *(eyebrow)* 0 - Angular compilers
- **H2** This is not a TypeScript decorator
- @Component({
- selector: 'cat-bean-grid',
- imports: [CurrencyPipe, DecimalPipe],
- templateUrl: './bean-grid.component.html',
- styleUrl: './bean-grid.component.scss',
- })
- export class BeanGridComponent { … }

**Spoken — 227 words, about 1:37**

A component decorator. A selector, two pipes it imports, a template file, a stylesheet, and a class underneath.

TypeScript does have decorators. Microsoft added them to the language years ago, and Alex Rickabaugh from the Angular team will tell you they were added largely because Angular needed them. So it would be reasonable to assume this is one of those.

It is not. This is Angular's own decorator, and it behaves nothing like TypeScript's.

A TypeScript decorator is a function. It runs. At runtime, when the class is defined, the function is called and it can do something to the class.

This one never runs. In the build that reaches your users it is not there at all — open the bundle and search for the word Component and you will not find it. It was read at compile time, by a compiler, and then deleted.

Everything inside those braces is metadata. A description. The selector is a description of how to find this component in HTML. The imports are a description of what the template is allowed to use. The HTML is metadata. The SCSS is metadata. None of it is code that runs.

So if it is a description rather than instructions, something has to read it and turn it into something that does run.

That something is what the next few minutes are about.

Here is the same component after compilation. Nothing is simplified except the parts replaced with an ellipsis.

Start at the top, because the top is the surprising part. Your class is still your class. The field is still a field. stockState is still an ordinary method, with the same ternary you wrote. If you pasted that class into the TypeScript playground with the decorator removed, you would get almost exactly these lines. The compiler did not touch your code.

What it did was add two static properties, and delete the decorator.

The first one, ɵfac, is the factory — how to construct this class, and what to inject when you do.

The second is ɵcmp, and this is where everything from the decorator went. The first property in it is type, and it points straight back at the class above it — this definition belongs to that class, and the runtime follows that reference in both directions. Then the selector is here. The inputs are here. And the template — the HTML file, the one sitting next to the component — has become a function.

Two arguments. rf and ctx. rf is a bitmask, and the function has two halves. One runs when the view is created and builds the DOM. The other runs on every change detection pass and updates it. The whole of Angular's rendering model is in those two lines: build once, update many times.

You do not need to read the instructions. What matters is the shape of what you are looking at — because this is plain JavaScript. Function calls and object literals. No decorator, no HTML, no SCSS, no Angular syntax of any kind. Every bundler on earth can read this.

The template syntax, the decorator, the separate files — all of that is for us. By the time it ships, it is a function.

# What the Angular compiler actually does, and why it has been married to TypeScript's compiler API for ten years.

## 4 · `ngtsc-wraps` — ngc is a superset of tsc

*Transition: fade*

**On screen**

- *(eyebrow)* 0 - Angular compilers
- **H2** ngc is a superset of tsc
- NgtscProgram
- wraps
- ts.Program
- NgCompilerHost
- wraps
- ts.CompilerHost
- NgCompiler
- drives
- every Angular-specific phase
- The Angular compiler wraps the TypeScript compiler — so everything Angular does to your code has to fit through TypeScript’s own compiler API.

**Spoken — 274 words, about 1:57**

So what is the thing that deleted your decorator? It is called ngc — the Angular Compiler — and it ships as a real command in at-angular-slash-compiler-cli. Alex Rickabaugh describes it as an extended TypeScript compiler which also knows how to execute Angular decorators, applying their effects at build time instead of run time.

You will see a second name on this slide, and it is worth one sentence so it does not distract you. Ngtsc is what the implementation is called inside Angular's source — ng, plus tsc — which is why these three classes are named the way they are. Same compiler. Ngc is what it is called from outside.

The architectural fact underneath that is this: it does not replace the TypeScript compiler, and it is not a fork of it. It wraps it. NgtscProgram wraps TypeScript's Program. NgCompilerHost wraps TypeScript's CompilerHost — that is how it sneaks in extra files, like the template type-checking shims. And NgCompiler sits on top and drives all the Angular-specific work.

Angular's own documentation puts it bluntly: the decorator is the compiler. @Component is not configuration that gets read at runtime. It is an instruction to a compiler, and the compiler's entire job is to turn it into something else.

Because it wraps TypeScript rather than replacing it, everything Angular does to your code has to fit through TypeScript's own compiler API. Angular does not get to invent its own way in. It uses the doors TypeScript leaves open.

That constraint is what gave Angular ten years of unusually good tooling — one compiler pass, one type system, Angular semantics and TypeScript semantics checked together.

## 5 · `phases` — ngc compiles the decorator

*Transition: fade*

**On screen**

- *(eyebrow)* 0 - Angular compilers
- **H2** ngc compiles the decorator
    | # | Phase | What it does | Half |
    | 1 | Detect | Find decorated classes | frontend |
    | 2 | Analyze | Read decorators and their metadata | frontend |
    | 3 | Resolve | Link each reference to the class it points at, across all files | frontend |
    | 4 | Type-check — components only | Templates become Type Check Blocks: TypeScript that tsc checks, then drops | backend |
    | 5 | Compile | Build definition functions. ɵɵdefineComponent() will be assigned to ɵcmp — nothing is written yet | backend |
    | 6 | Emit | Put definitions in the class, delete the decorator, print the output — runs as a ts.Transformer | backend |
- All six run for every decorated class — component, directive, pipe, service.
- The backend produces two outputs from the same analysis: the type-check blocks, and the code that replaces the decorator.
- Frontend — understands decorators and how they are interconnected. Global and slow.
- Backend — transforms file by file. Local and fast.

**Spoken — 521 words, about 3:43**

Six phases, and every decorated class goes through all six.

Every phase here exists to compile the decorator. That is the entire job. Your class body, your methods, your types — none of that enters this pipeline. It goes through TypeScript exactly as it always would.

And it is every decorator, not only components. A pipe goes through these six. A service goes through these six. Only the template work is component-only.

Detect finds the decorated classes. Analyze reads what is inside each decorator.

Resolve is the one that needs the rest of your program. A template says cat-bean-grid, or uses the currency pipe, and the compiler has to find the class behind that name. The answer is not in the file. It is spread across your imports and your NgModules, so this phase cannot finish until it has seen everything.

Those first three are the whole of the frontend. Nothing has been written anywhere yet — it is all metadata, held in memory.

Everything after them is the backend, and the backend's job is to generate code. It does that twice, from the same analysis, and the two outputs do not depend on each other.

The first is the one nobody guesses. TypeScript cannot read Angular templates. So Angular rewrites each template as TypeScript — a Type Check Block — lets TypeScript's own checker find the errors, maps them back onto your HTML, and drops the blocks. They never reach disk and they never ship. That is where the error comes from when you misspell a property inside double curly braces.

The second output is the code that actually runs. Two phases build it, and they look like one. The difference is small but it is worth having.

Compile builds the definition. For a component, defineComponent gets built, ready to be assigned to ɵcmp. But at the end of compile nothing has been written anywhere. It is an object in memory, in Angular's own format. Your class has not changed yet and your decorator is still on it.

Emit is where it lands. Angular translates that object into TypeScript's own form, puts it on the class as a static property, deletes the decorator, and prints the file.

So compile makes the content. Emit makes the file.

And emit is the only one of the six that writes back into TypeScript. It runs as a TypeScript custom transformer — ts.Transformer. The first five read from TypeScript's compiler; this is the one that hands it something. Angular gives TypeScript a function, and TypeScript calls it during its own emit.

One detail that surprises people: what gets printed is not always JavaScript. This repository sets isolatedModules, which tells Angular to apply only its own transformation and leave the rest of the TypeScript alone. So what the bundler receives here is TypeScript, and esbuild or Rspack does the rest.

Now the two halves. The frontend understands the decorator: global, and slow, because it cannot finish until it has seen everything. The backend writes code — both kinds of it: file by file, and fast. Only one of those halves has been rewritten so far.

# TypeScript 7 removes that API, so Angular is building a new compiler that leaves a file behind instead of running inside the bundler.

## 6 · `ts7` — The APIs Angular needs are gone

*Transition: push*

**On screen**

- *(eyebrow)* 0 - Angular compilers
- **H2** The APIs Angular needs are gone
- “The Angular compiler implements its own code transformations via the ts.Transformer API which is not available cross-language.”
- Angular blog · An update on Angular’s TypeScript 7-powered Compiler · September 2026
- 1
- TypeScript 7’s compiler is a program written in Go. Stable since July 2026.
- 2
- ts.Transformer is only possible while both sides are JavaScript.
- 3
- Go and JavaScript cannot share objects. So those APIs cannot be made public again

**Spoken — 290 words, about 2:04**

And then this happened.

TypeScript 7 shipped in July. Same language, same type system, but the compiler itself has been rewritten in Go, and it is roughly ten times faster.

Here is the Angular team's own sentence about what that costs them. The Angular compiler implements its own code transformations via the ts dot Transformer API, which is not available cross-language.

Three steps to see why, and they are worth taking slowly.

One. The new TypeScript compiler is a Go program. Not JavaScript that got faster — a different language, compiled to a binary.

Two. ts.Transformer is not a file format and it is not a protocol. It is TypeScript calling a JavaScript function that Angular supplies, handing it a live object — the syntax tree — letting Angular rearrange that object in place, and then carrying on with the result. Both sides are JavaScript. Both sides are in the same process. They are pointing at the same objects in the same memory.

Three. Go and JavaScript cannot do that. You can send data between them — text, JSON, bytes down a pipe. What you cannot do is hand a Go program a JavaScript function and have it call you back with a live tree.

So this is not an API that got harder to use, or changed shape, or needs a wrapper written for it. A set of APIs that used to be public simply cannot be public any more, because there is no way to express them across two languages. Angular will use TypeScript 7's interop for type-checking and diagnostics, where sending data is enough. For compilation and transformation, sending data is not enough.

Which means the capabilities TypeScript used to provide, Angular now has to provide itself.

[Read the quote aloud, then count the three points on your fingers. Point two is the one that does the work.]

**Spoken — 489 words, about 3:30**

So if the way in is closed, you stop going in. You build your own compiler.

That is what this is. It is called ngp, it has been in Angular's main branch since the eighth of October, and their own README opens with the word Caution: early-stage prototype, not accepting outside contributions. So nothing here is a promise.

Two things changed. One is interesting. The other is the one that matters.

The interesting one is the frontend. The orange half — the global, slow half — has been rewritten in Rust, on oxc — the same toolchain underneath Vite. It is multithreaded, which is why it will be fast. The blue half did not move: the backend is still TypeScript, still the same template compiler Angular has always had. What changed in it is only the last step. The old backend handed its result to TypeScript, through ts.Transformer, which is why it had to run inside TypeScript. The new one prints the characters into a file. That is the whole reason it can stand on its own.

The one that matters is in the shape of the picture, not in either box.

Look at the top row. The compiler is inside the bundler. That was not a design choice anybody made for fun — it was forced. Angular's output never existed anywhere you could pick it up. It was a syntax tree, inside a running TypeScript process, for a few milliseconds. The only way to receive it was to be in that process, as a plugin. So the bundler had to host Angular's compiler inside itself.

Which is why every bundler that builds Angular needs an adapter written specially for it. Somebody has to write the plugin that drives the compiler and hands the results around. That is what @nx/angular-rspack is. That is what the Analog plugin is for Vite. Somebody maintains each one.

Now look at the bottom row. The compiler runs first, on its own, and leaves two files behind — one per job. The ng dot ts file is your code with the decorator already replaced; that is what the bundler takes. The ngtypecheck file is the templates rewritten as TypeScript; that is what tsc takes, to give you template errors. Same two jobs as before, but now each one ends in a file instead of inside somebody's process. And that is not a plan — it is already there. There is a command in the branch today: you point ngp at a tsconfig, give it an output directory, and it writes you a folder of TypeScript. No bundler involved, nothing hosting anything. Ordinary TypeScript, with the decorator already replaced by the definition.

The bundler is no longer hosting anything. It is just reading TypeScript — which every bundler on earth already does. esbuild reads it. Rspack reads it. Vite reads it. Something you write this afternoon reads it.

The adapter has nothing left to adapt.

# The bundler is already a choice — the same product built three ways on Angular 22, and the one question all three answer differently.

## 8 · `three-ways` — Angular does not require esbuild

*Transition: push*

**On screen**

- *(eyebrow)* 0 - Angular compilers
- **H2** Angular does not require esbuild
    | Pipeline | The Angular plugin it loads | Bundler |
    | angular.json — ng build · the default | @angular/build | esbuild |
    | rspack.config.ts — rspack build | @nx/angular-rspack | Rspack |
    | vite.config.ts — vite build | @analogjs/vite-plugin-angular | Rolldown |
- A custom pipeline is a config file and a plugin. The plugin catches every .ts before the bundler reads it, runs the Angular compiler, hands back the result.

**Spoken — 362 words, about 2:35**

So the bundler is becoming a choice. Except that it already is one, and has been for a while.

The previous slide said that a bundler can only build Angular by hosting the Angular compiler inside itself, as a plugin. That sounds like a reason nobody would bother. People bothered.

Read this table left to right, because that is the order the decision happens in. You pick a pipeline. The pipeline loads an Angular plugin. The plugin determines which bundler ends up doing the bundling.

The top row is the one everybody has. A file called angular dot json, the command ng build, the plugin at-angular-slash-build, and esbuild underneath. Most people have never needed to know the last two are there.

The other two rows are custom pipelines, and that phrase is doing real work. There is no angular dot json involved and the ng command never runs. The second row is a file called rspack dot config dot ts and the command rspack build, which loads a plugin from Nx, and lands on Rspack. The third is vite dot config dot ts and vite build, which loads the plugin from the Analog project, and lands on Rolldown.

That third one is worth one word of precision. Vite is not a bundler — it is a build tool. The bundler underneath it is Rolldown. Which is why the third column says Rolldown and not Vite.

So how does any of this actually work? All three plugins do the same job, through three different plugin APIs. Each registers with its bundler and says: before you read a TypeScript file, hand it to me first. The plugin runs the Angular compiler on it and gives back the result. esbuild calls that hook onLoad. Vite calls it transform. Rspack does it through a plugin of its own.

That is what hosting the compiler means, concretely. The Angular compiler never runs on its own here. It runs as a function the bundler calls, in the middle of the bundler's own work.

Which also tells you why there has to be one of these per bundler. The compiler is the same every time. The hook is not.

# A specifier is a name, not a location. What kinds exist, and the three moments at which something can resolve one.

**On screen**

- *(eyebrow)* 1 - Modules
- **H2** Let us start from the beginning
- import { Component } from '@angular/core'
- That quoted string is a specifier. It names a module — in practice, a file — but says nothing about where that file is.

**Spoken — 189 words, about 1:21**

So: who turns that string into a file?

Here is a line that has to appear in every component file ever written, because the decorator has to come from somewhere. Import Component, from at-angular-slash-core.

Look at the part in quotes. That string has a name — it is called a specifier — and the thing worth noticing is what it is not.

It is not a path. It is not a file name. It is not a URL. There is no folder called at-angular-slash-core sitting on a disk somewhere, and there is certainly no file by that name on a web server.

It is a name. Somebody, at some point, has to look that name up and decide which actual file it means.

A browser cannot do that on its own. Hand a browser that string inside an import and it will refuse it — failed to resolve module specifier — because as far as the web platform is concerned, that is not an address at all.

So something has to resolve it. What that something is, and when it runs, is not the same in every Angular application.

    | Type | Example |
    | Relative URL path | ./util.js |
    | Absolute URL path | /lib/util.js |

- The first three tell a browser where the module’s file is. A bare specifier does not.

**Spoken — 184 words, about 1:19**

There are four types, and the difference between them is the whole of this section.

A relative URL path. Dot-slash util-dot-js. Relative to the file doing the importing.

An absolute URL path. Slash-lib-slash-util-dot-js. From the root of the site.

A full URL. A complete address, pointing at any server you like.

And a bare specifier. At-angular-slash-core — the one from the slide before.

The first three are locations. A browser can take any of them and go and fetch the file, with no help from anybody. The third one could be pasted into an address bar.

The fourth is not a location. There is no server anywhere with a folder called lodash. It is a name, and names have to be looked up by somebody.

And this is the type that matters here, because it is the only one a browser cannot resolve by itself. At-angular-slash-core. Rxjs. Names, with no location attached.

Which is why handing a browser a bare specifier gets it refused — failed to resolve module specifier. Not because the file is missing. Because nothing ever told it where to look.

## 11 · `static-dynamic` — Static imports and dynamic imports

*Transition: fade*

**On screen**

- *(eyebrow)* 1 - Modules
- **H2** Static imports and dynamic imports
- *(eyebrow)* Static
- import { Component } from '@angular/core';
- Only at the top of a file. — The specifier must be a literal string, so the whole graph is known before anything runs. — This is what tree-shaking is built on.
- *(eyebrow)* Dynamic
- const routes = await import('./catalog.routes');
- Anywhere code can go. Returns a promise. — Resolved when the line runs. — The specifier can be a variable.
- A static specifier is known before the program starts. A dynamic one does not have to be.

**Spoken — 241 words, about 1:43**

A specifier does not only turn up in one place.

On the left is the one everybody knows. A static import, at the top of the file. The specifier is written there as a literal string, and it cannot be anything else. You cannot build it, you cannot pass a variable, you cannot read it from a configuration file.

That restriction sounds like a limitation. It is actually what makes the whole build pipeline possible. Because every static specifier is a literal, a tool can read your entire program without running a single line of it, follow every import, and know the complete list of files in advance. That is what lets a bundler build a graph. It is also what lets it shake the tree, because it can see what is never reached.

On the right is the other one. A dynamic import. It is not a statement, it is an expression — it goes anywhere a function call can go, and it hands back a promise.

And its specifier is not required to be a literal. It can be a variable. It can be assembled from a string. It can be a value that did not exist anywhere when the application was compiled.

So the difference that matters is this one. A static specifier is known before the program starts. A dynamic specifier does not have to be — it can be decided while the application is already running.

**Spoken — 217 words, about 1:33**

Three moments, one at a time. This is the first, and it is the one almost everybody is already using without thinking about it.

At build time, the bundler does the resolving. It reads a specifier, goes looking on the file system, finds the package inside node_modules, and writes the answer into the output.

Here is what that looks like. On the top line, what was written in the source: at-angular-slash-core. On the bottom, the file that came out of the build. The bundler has taken the package, bundled it into a chunk, given it a name of its own and a content hash so it can be cached forever.

Which is the thing to hold on to, and the reason the other two moments exist at all. The bundler could do this because node_modules was sitting right there. A browser has no node_modules. It has never had one, and it never will. So the moment you want a name resolved anywhere other than at build time, somebody has to answer the question a different way.

Second moment. This one is a browser feature, and a surprising number of people have never seen it.

It is a script tag, with a type of importmap, and inside it a piece of JSON. The JSON says: when any module asks for at-angular-slash-core, fetch this file instead. When anything asks for rxjs, fetch that one.

That is the whole mechanism. There is no library here. Nothing was installed. This is the browser's own module loader doing the lookup, using a table it was handed.

Two things are worth knowing about it.

The first is timing, and it is strict. The map has to be in the document before the first module import runs. Not shortly after. Before. Which is why applications that rely on it split their startup into two files — one tiny script that installs the map, and then a second one that actually starts the application.

The second is that it is not new and it is not experimental. Import maps are a web standard and they have worked in every major browser since 2023. No polyfill, no bundler plugin, no runtime.

So here a bare specifier does reach the browser, and the browser can resolve it — because somebody handed it the answers in advance.

Third moment, and this is the one that behaves differently from the other two.

Here the resolving is done by code. Not by a bundler on somebody's machine, not by the browser's loader — by JavaScript that was shipped as part of the application and is running right now.

Two lines. The first asks something for an address. That something could be anything: a registry object, a fetch to a JSON file on a server, a lookup in a table that was downloaded a second ago. The second line takes whatever came back and imports it.

And the important word in that is whatever. The address on the second line did not exist when this application was compiled. Nobody wrote it down. It was not in any configuration file that went through the build. It arrived while the application was running, and the application acted on it.

That is a genuinely different capability from the other two moments, and it is the reason this one needs a dynamic import. A static import needs a literal string, decided before anything runs. This cannot be a literal, because the value is not known yet.

So: three moments. The bundler, before anything ships. The browser's loader, before the application starts. And code, while it is already running.

Three answers to the same question. Which one an application picks turns out to decide a great deal about how it is built, how it is deployed, and what can change without rebuilding it.
